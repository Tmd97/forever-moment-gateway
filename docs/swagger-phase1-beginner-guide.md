# Swagger Phase 1 Implementation Guide

> Audience: beginner Java developers (with additional notes for senior/architecture thinking)
>
> Scope covered in this phase:
> 1. Persist authorization token in Swagger UI (`persist-authorization`)
> 2. Define JWT bearer security scheme in OpenAPI
> 3. Apply default security requirements for protected APIs while keeping public APIs open

---

## 1) Why this phase matters

Before this phase, teams usually face these pain points:
- Swagger asks for token repeatedly after browser refresh.
- Different services document auth differently (or not at all).
- Frontend/QA are unsure which endpoint is public and which needs JWT.
- New developers can call APIs, but do not understand auth expectations quickly.

Phase 1 solves those operational and onboarding issues without changing runtime business behavior.

---

## 2) Core concepts (simple language)

### 2.1 OpenAPI vs Swagger UI
- **OpenAPI** = API contract/specification (machine-readable, JSON/YAML generated by annotations/config).
- **Swagger UI** = visual web page that renders OpenAPI and lets you try APIs.

### 2.2 Security scheme (what it is)
A **security scheme** tells Swagger UI *how authentication is supplied*.

For JWT bearer token, the scheme is usually:
- type: `http`
- scheme: `bearer`
- bearerFormat: `JWT`

This makes Swagger show an **Authorize** button.

### 2.3 Security requirement (where auth is required)
A **security requirement** says *which operations need auth*.

Common model:
- protected APIs → require bearer JWT
- public APIs → explicitly no requirement

### 2.4 Persist authorization (quality-of-life config)
`springdoc.swagger-ui.persist-authorization=true` tells Swagger UI to keep the entered token across page refreshes (browser storage-backed behavior).

## 4.2 Service-level expected Phase 1 pattern

Each business service should follow this same pattern:

1. **Enable token persistence**
   - in `application.yml` or equivalent:
   ```yaml
   springdoc:
     swagger-ui:
       persist-authorization: true
   ```

2. **Define JWT bearer scheme**
   - using annotation-based config (`@SecurityScheme`) or OpenAPI bean.

3. **Apply default security requirement**
   - protected controllers/operations require JWT.
   - public controllers/operations explicitly set as unsecured.

## 5) Reference implementation patterns

You can implement with either annotation-first or bean-first style.

## 5.1 Annotation-first (simple and readable)

```java
@Configuration
@SecurityScheme(
    name = "bearerAuth",
    type = SecuritySchemeType.HTTP,
    scheme = "bearer",
    bearerFormat = "JWT"
)
public class OpenApiSecurityConfig {
}
```

Then apply requirement at class/operation level:

```java
@SecurityRequirement(name = "bearerAuth")
@RestController
@RequestMapping("/admin")
public class AdminController { ... }
```

For public operations:

```java
@Operation(security = {}) // explicit no-auth in docs
@GetMapping("/public/health")
public String health() { ... }
```

## 5.2 Bean-first (useful for global metadata)

```java
@Bean
public OpenAPI customOpenAPI() {
    return new OpenAPI()
        .components(new Components().addSecuritySchemes("bearerAuth",
            new SecurityScheme()
                .type(SecurityScheme.Type.HTTP)
                .scheme("bearer")
                .bearerFormat("JWT")))
        .addSecurityItem(new SecurityRequirement().addList("bearerAuth"));
}
```

Then override public operations with empty security.

## 7) How to verify implementation (manual checklist)

Run this checklist per service and gateway:

1. Open Swagger UI.
2. Click **Authorize** and paste JWT.
3. Call a protected API successfully.
4. Refresh browser.
5. Verify token still present.
6. Try protected API again without re-entering token.
7. Confirm a public API works with no token.
8. Confirm docs visually indicate which endpoints are secured.

## 7.1 Repo-by-repo verification walkthrough (beginner friendly)

Use this sequence exactly:

1. Start Consul + gateway + one service (Platform/Booking/Payment).
2. Open that service’s Swagger UI and gateway Swagger UI.
3. Click **Authorize**, paste a valid JWT, and run one protected API.
4. Refresh the browser tab.
5. Confirm the token is still present.
6. Run protected API again; it should still authorize.
7. Validate public endpoint behavior:
   - Platform: any `/public/**` or `/auth/**` operation should appear open in docs.
   - Payment: Stripe webhook endpoint should appear open due to explicit override.
8. Repeat for remaining services.

What success looks like:
- Token survives refresh in all UIs where `persist-authorization` is enabled.
- Protected operations show lock/auth requirement.
- Public operations do not falsely require bearer auth.

## 8) Common mistakes and how to avoid them

### Mistake 1: defining scheme but never applying security requirement
Result: Authorize button exists, but operations still appear open.

Fix: Apply `@SecurityRequirement(name="bearerAuth")` globally or on protected controllers.

### Mistake 2: applying global security but forgetting public overrides
Result: login/public endpoints wrongly look protected.

Fix: Add per-operation `@Operation(security = {})` or controller-level public config.

### Mistake 3: inconsistent scheme name
Result: requirement references unknown scheme.

Fix: use one canonical key, e.g. `bearerAuth`, everywhere.

### Mistake 4: treating Swagger docs as runtime auth enforcement
Result: false confidence.

Fix: remember OpenAPI docs are descriptive; runtime security still enforced by filters/security config.

## 9) Public vs protected API documentation strategy

A practical team convention:
- package controllers under `controller.pub` and `controller.admin/user`
- apply security requirement by package/controller role
- require explicit public declaration for any unauthenticated endpoint

This prevents accidental exposure and keeps docs easier to audit.

## 11) Q/A for beginner developers

### Q1: If Swagger shows an endpoint as secured, is backend always secure?
Not automatically. Docs reflect configuration and annotations; actual enforcement depends on gateway/service runtime security.

### Q2: Why do we need both gateway and service Swagger docs?
Gateway gives one unified view; service docs help deep debugging and service-local development.

### Q3: Why does Bearer token start with `Bearer ` prefix?
HTTP Authorization header convention for bearer scheme.

### Q4: Is storing token in Swagger UI secure?
It is a developer convenience. Use only in trusted local/dev environments; follow org security policies for shared machines.

### Q5: Why keep public APIs explicitly marked?
To avoid accidental locking/unlocking during refactoring and to make intent clear for QA/frontend.

## 13) Suggested coding standards for future Swagger work

1. Every controller method must have:
   - `@Operation(summary=..., description=...)`
   - explicit success/failure `@ApiResponse`
2. Every request/response DTO field should have `@Schema(description=..., example=...)`
3. Every protected endpoint must declare/inherit security requirement.
4. Every public endpoint must explicitly declare no security requirement.
5. Keep examples realistic and production-safe (no real secrets).
